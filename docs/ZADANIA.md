# Zadania dla agenta (priorytety)

Kolejność = rekomendowana. Każde zadanie: cel, gdzie, kryterium „zrobione”. Wszystko, co dotyka zapisu do kotła, wymaga świadomej zgody właściciela i próby na kotle z nim.

1. **Android: parowanie tokenem, wiele urządzeń, mDNS.** `android/app/src/main/java/pl/tekla/pellet/` (`Source.kt`, `App.kt`, `MainActivity.kt`). Zrób: lista urządzeń (klucz = `id` z `/api/identity`), wykrywanie przez NSD (`_teklapellet._tcp`, TXT: id, name, fw, api, node), ręczne dodanie po adresie, pierwsze połączenie `POST /api/pair` hasłem → zapis tokenu (np. `EncryptedSharedPreferences`/Keystore, **nie** hasła), potem samo `Authorization: Bearer`, sprawdzenie `api == 2`, wybór aktywnego urządzenia, odwołany token (401) → ponowne parowanie. Tryb demo zostaje jako osobne „urządzenie”. *Gotowe, gdy:* APK buduje się w CI, demo działa, a przeciw `tools/mock/server.js` da się sparować, przełączać urządzenia i zobaczyć dane.
2. **Android: ekran modułu pod nowe API.** Operacje serwisowe wymagają najpierw `POST /api/service/unlock` (hasło, 5 min); Wi‑Fi, IP/DNS (z `POST /api/net/confirm` po zmianie adresu), nazwa, klienci (lista/usuń), hasło, restart/reset (`confirm:"RESET"`). Dziś ekran używa starego wzorca (hasło w każdym żądaniu).
3. **Klient Windows** (decyzja właściciela: „aplikacja na Windows”). Baza: `ui/` + `ui/gen/app.json`; wybierz technologię (np. WebView2/Tauri/Electron albo natywnie). Ten sam kontrakt co Android: `docs/API_ESP.md`. Parowanie tokenem i wiele urządzeń jak w pkt 1.
4. **Integracja Home Assistant** (`ha/`). Config flow z zeroconf (`_teklapellet._tcp`), unikalny klucz = `id` urządzenia, encje z `docs/interfejs_kompletny.json`/modelu, PIN/tryb zapisu jak w API. Nie zmieniaj istniejących `entity_id` po wydaniu.
5. **CI: publikacja kanału BETA.** Workflow na gałęzi `beta`: budowa, podpis (`tools/ota_sign.py sign`), wydanie GitHub `beta` z `tekla_pellet_beta.bin` (obraz + 64 B podpisu) i `beta.json` (`{"version": "..."}`). Wymaga sekretu z kluczem prywatnym (zakłada właściciel) i wstawienia klucza publicznego do `esp/main/ota_pubkey.pem`. Klucza prywatnego **nigdy** do repo.
6. **ESP: historia alarmów.** Odczyt rejestrów `0x4011‑0x404B` (`analiza/.../ui_model/alarms.json`, `alarm_codes_verified.json`), endpoint `/api/alarms` ma zwracać wpisy (`n, code, text, active, acked`).
7. **ESP: wykrywanie konfliktu węzła CAN** (domyślnie 95) przy starcie: nasłuch heartbeatów, ostrzeżenie w `/api/identity`/logu.
8. **Weryfikacja na sprzęcie (z właścicielem)**, lista kontrolna: start i CAN (odczyt PID 0x2001), mDNS i parowanie, zmiana Wi‑Fi (w tym nieudana → powrót), zmiana IP (bez potwierdzenia → powrót), awaryjny AP, OTA z pliku i rollback, kanał BETA po HTTPS, dopiero potem zapis jednego bezpiecznego parametru z odczytem zwrotnym, harmonogram, test wyjść. Wyniki dopisz do `docs/STATUS.md`.
9. **Zgodność wyglądu z panelem** (opcjonalnie): porównanie ekranów z atlasem `analiza/analiza_archiwum/FW2213TK-2026-11-22/data/ui_model/atlas/`. Wygląd klientów to decyzja budującego; panel jest źródłem **zawartości i zachowania**.

## Stałe zasady przy każdym zadaniu
Minimalne zmiany; testy po zmianie (`sh esp/components/tekla_core/test/run.sh`, `node tools/mock/e2e.js`, kompilacja w CI); po zmianie `data/` lub `tools/app_spec.py` regeneracja (`tools/gen_esp_tables.py`, `tools/gen_app_model.py`) i kopia do `android/.../assets/`; nie zmieniaj kontraktu API bez aktualizacji `docs/API_ESP.md` i serwera‑atrapy; raport: WYKONANE / ZMODYFIKOWANE PLIKI / ZACHOWANE / WERYFIKACJA / SKUTKI UBOCZNE / DO SPRAWDZENIA PRZEZ UŻYTKOWNIKA.
